# Security

- SSH host keys are pinned per hostname/port after explicit user confirmation. A mismatch is rejected; there is no permissive fallback.
- Each device logs in with a password or with the phone's SSH key (see "SSH key login" below). Passwords are only persisted when the user chooses to remember them, encrypted together with device profiles using AES-GCM and an Android Keystore key. Passwords are never returned by the device-list API, logged or copied to the clipboard. Changing the host, port or username does not reuse a saved password. Android backup is disabled. Screenshots are allowed by default (the user asked for it); 设置 → 防截图 sets FLAG_SECURE on every screen, which also hides the app in the recent-apps preview. Password fields are always masked.
- The public bridge source is bundled with the app. Install requires an explicit action, uses SFTP, verifies uploaded bytes, and names the file by SHA-256. No downloaded remote installer is executed.
- SSH requests have timeouts and bounded response size. Prompt input is bounded and passed as one subprocess argument, never evaluated as shell code.
- Only existing running sessions and recognized agents are targeted. The bridge does not run arbitrary shell commands, create agents, stop or restart Herdr servers, or bypass approval dialogs. It starts the Herdr server only on an explicit 「启动 Herdr」 tap or through the opt-in 「Herdr 守护」, and only while no server is running (see "Starting Herdr and the Herdr guard" below).
- tmux: only the SSH user's own tmux servers — the default one and named ones whose sockets are in that user's tmux socket directories (see "tmux sessions" below). 「新建 tmux 会话」 runs `tmux new-session -d [-s NAME] -c DIR` as an argv list (name limited to letters, digits, `-`, `_`; the directory, given as an absolute path, `~`, `~/…` or relative to the home directory, may be any existing directory the SSH user can enter; see "Start directories" below); it may start that user's default tmux server (never a named one). 「关闭」 runs `kill-pane` or `kill-session` only on a pane whose identity (server pid, pane id, pane pid) still matches, and never ends a session that holds the Herdr client. Input to a Claude/Codex found in a tmux pane is bound to that agent process (pid and start time) and goes through the same receipts. Its state is read from its screen (a menu = waiting, "esc to interrupt" = working): a prompt goes in only while it reads idle (the phone queues otherwise), a question is answered with `tmux send-keys` one key at a time with a screen re-read after each and Enter only on a verified cursor (the same rules as Herdr panes), Shift+Tab only while its own input footer is on screen and no dialog waits, and pictures/files are named by local path after the same hash checks. The background watcher may read these panes (status and screen only) and never sends them anything.
- Mutations require a UUID. A private SQLite receipt is committed before invoking Herdr. If a process dies, a retry with the same ID refuses to execute again. The app never automatically retries a mutation. A user manually submitting again generates a new ID; inspect output first after unknown outcomes.
- The bridge stores hashes and receipts under `~/.local/state/herdr-pocket`, not prompt text. Receipts are not automatically pruned yet.
- SSH credentials authorize the user's full account outside this application. The bridge is not a sandbox and cannot constrain someone who independently has SSH access.
- Physical machinery, irreversible actions, and third-party project safety requirements still require their own authorization. A remote Enter is a real keypress.

For a vulnerability, use GitHub private vulnerability reporting if enabled, or contact the repository owner without posting credentials or exploit details publicly.

## Start directories and the directory tree (新建会话 / 新建 tmux 会话)
- A new Herdr tab or tmux session may start in **any existing directory the SSH user can enter** (search permission, `os.access` X_OK): under the home folder or anywhere else (`/mnt/…`, `/srv/…`), hidden folders included, named directly or through a symlink (`~/work` → `/mnt/E/work`). The user asked for this: the same account can already `cd` there over SSH, so limiting it to the home folder added no protection. Before anything is written the bridge resolves the path with `realpath` and checks that it exists, is a directory and can be entered; `~user`, `..`, control characters, a missing path, a dangling link and a non-directory are refused with a `没创建：…` message. The resolved path is passed to `tmux new-session -c` or `herdr … --cwd` as one argv item; nothing is run through a shell, and the directory choice runs no command in it.
- The phone's 「浏览目录…」 tree reads directories with the read-only `dirList` op: folder names only (never file names, sizes, times or contents), classified without following symlinks; a symlink is shown with its target and followed only when it leads to a directory. Results are capped (500 folders per directory, 20000 entries looked at), hidden folders are shown only on request, and each directory is read in a separate, killable child process with a deadline so a slow or dead network mount cannot hang the bridge. It sees what the SSH user can list, the same as `ls` in that account; it writes nothing and keeps nothing on the computer or in the phone's cache.

## SSH key login

- The app holds one SSH identity for the whole phone (like a person's `~/.ssh/id_ed25519`): every computer already trusts the same phone, so per-computer keys would add bookkeeping without protection. A computer is revoked by removing the line from its `authorized_keys`; 「重新生成」 (with a confirmation) revokes all at once.
- New keys are Ed25519, generated on the phone with JSch/BouncyCastle. The private key is serialized as an OpenSSH key and stored only as AES-GCM ciphertext (with associated data) under a separate, non-exportable Android Keystore key `pocket.identity.v1`, in its own preferences file, excluded from backup. It is decrypted into a byte array only for one SSH handshake (connect, silent reconnect, or the post-install test login) and wiped afterwards; JSch's parsed copy is dropped with `removeAllIdentity()` once authentication is over. There is no export, display, clipboard or log path for the private key; the WebView only ever receives the public key line and its SHA-256 fingerprint.
- Importing an existing key is optional: the file is picked with the system document picker and read natively (≤ 16 KB, OpenSSH / PEM / PKCS#8; Ed25519, ECDSA, RSA ≥ 2048), never passed to the WebView. A passphrase-protected key needs its passphrase, which is used once to decrypt and not stored; the key is then re-sealed under the Keystore key like a generated one. Public-key files, DSA and short RSA keys are refused.
- A key device stores no password (choosing 「密钥」 deletes a saved one), connects and reconnects without any password, and uses public-key authentication only. Host-key pinning is unchanged: the same pinned key is required for key logins and silent reconnects.
- 「装公钥」 writes to the connected computer only after a confirmation sheet that shows the exact line and what will be done; native code re-checks that the line is still the phone's current key. Over SFTP on the existing password session it creates `~/.ssh` (0700) if missing, appends that one line to `~/.ssh/authorized_keys` unless the same key type and blob are already present (no duplicates), gives a new file 0600 and only removes group/other write bits from an existing `~/.ssh` or file. It reads the file back to confirm the line, never edits or removes other lines and touches no other file. It then tries one key login on a separate session and reports the result; switching the device to key login (and deleting its saved password) is a separate, explicit choice.
- A rejected key reports `key_rejected` with the next step (install the public key; check `~/.ssh` 700, `authorized_keys` 600, home not writable by others); a computer without public-key auth reports `key_method`. Anyone with this unlocked phone and the app can log in to computers that trust its key, exactly as with a saved password.

## Jump hosts (跳板机)

- A device can be reached through up to three jump hosts, like `ssh -J`. The phone logs in to the first one over TCP; every next login runs inside a `direct-tcpip` channel of the previous SSH session. Nothing listens on the phone (no local port forwarding), agent and X11 forwarding stay off, and only the last login (the device) runs the bridge, SFTP and the terminal.
- Every login checks its own pinned host key with the same rules as a direct device: a new key needs an explicit 「信任并连接」 for exactly that key (one sheet per hop, in route order), a changed key is refused, and silent reconnects never trust a new key. The first hop keeps the plain `host:port` pin; a later hop is pinned by the whole path (`a:22>b:22`), because the same address behind a different jump host can be another machine.
- Each jump host logs in with its own password or with the phone's SSH key. A jump host's password is entered in the device form and stored only in the encrypted device vault (same AES-GCM / Keystore protection as a remembered device password); the device list returns only whether one is saved. It is kept only while that hop's address, user and everything in front of it stay the same; changing the route also drops the device's own saved password.
- Errors name the hop that failed. A reconnect, keepalive failure or disconnect rebuilds or closes the whole chain (innermost session first); requests follow the same never-replay rules as a direct connection.

## Reconnects and background alerts

- A silent reconnect only uses the host key already pinned for that host and port; a changed key stops reconnecting and is reported. It never shows a new trust prompt on its own.
- The password for a reconnect comes from the encrypted vault, or, if the device does not remember it, from memory for the current app process only. It is cleared on disconnect. Key devices reconnect with the Keystore-sealed key and need no password.
- A request is re-sent after reconnecting only when it provably never reached the host: the session was already down, or the exec channel failed to open (stdin is streamed only after the channel opens). Anything that failed after being written keeps the "outcome unknown" error and is never replayed.
- Reconnecting ends the previous interactive SSH shell; it is not resumed.
- Several computers can be connected at the same time (at most 4). Each has its own SSH session, pinned host key, password-in-memory and reconnect state; nothing is shared between them, and the rules above apply to each one separately. Every device-bound request from the page names its computer and is refused if that computer is not connected; a queued message is bound to the computer it was written on and is only sent while that computer is on screen. Disconnecting one computer leaves the others connected; 断开 on the notification ends all of them.
- 启动时自动重连 (设置 → 连接, on by default): the app remembers, in app-private preferences, only the ids of the computers that were connected and which one was on screen (no names, addresses or secrets). A connect adds a computer; an explicit 断开 / 全部断开 (in the app or on the notification) or deleting the device removes it, so it is not reconnected; the app being killed, swiped away or updated keeps the list. On the next launch those computers reconnect one after another (the one that was on screen first), but only when nothing has to be asked: a saved password or key login for the computer and every jump host, and every host key already pinned. The native side checks this again and never shows a trust prompt, password prompt or bridge install for a quiet reconnect; such a computer only gets a row on its device card, and a tap runs the normal connect. A changed host key stops it like a silent reconnect. Network failures are retried only when the network comes back or changes or the app returns to the foreground, at most three tries per launch. Computers still held by the keep-alive service are reused, not connected again.
- The background watcher is a foreground service with a visible notification and a stop action. It only runs the read-only `status` operation (with `tmux: true` it also reads the screens of Claude/Codex panes in tmux; for Herdr, idle/done Claude/Codex screens are looked at for a dialog Herdr missed, see PROTOCOL "Dialogs Herdr does not see", keeping only terminal ids and timestamps in `~/.local/state/herdr-pocket/screens-v1.json`), never sends prompts or keys, and stops when the app returns to the foreground, on disconnect, after five consecutive failures or after eight hours. Notifications contain the agent title and state only, not message content.

## Pictures and files sent from the phone

- Pictures and files are uploaded with SFTP into `~/.herdr-pocket/uploads/<UTC day>/` only (folders 0700, files 0600); a file keeps its sanitized original name inside a folder named after the first 16 hex characters of its SHA-256. Names are checked again by the bridge (one path segment, no leading dot, no control/format/bidi or line-separator characters, ≤ 180 bytes), so they cannot traverse paths or hide lines in a prompt. Symlinked folders or files are refused. Files are streamed from the system document picker without a storage permission and never pass through the WebView.
- The bridge re-hashes every upload before naming it in a prompt, and the prompt only carries paths, not file contents. Uploads older than 14 days are deleted opportunistically, and only the file kinds the phone writes.
- For a pane attached to another computer through ch-cli, files are copied there **before** the prompt, through the same live route used for remote history (`BatchMode=yes`, strict host-key checking, forwarding disabled, no control master). This writes to the other computer, confined to that SSH user's `~/.herdr-pocket/uploads/<day>/<prefix>/<name>`: real non-symlinked folders owned by the user, created with umask 077, a size and SHA-256 check, and no replacement of an existing different file. Any failure (unreachable, timeout, mismatch) stops before the prompt with a "没发出去" message, so nothing reaches the agent. Panes that SSH elsewhere without a ch route are refused. Pictures for ch routes still use `ch share-image` (`ch` has no command for other files).

## 文件: uploading and downloading over SFTP

The 文件 screen browses a connected computer and moves files both ways. It is SFTP on that computer's existing SSH session (jump hosts included); no FTP server, no extra port, no bridge and no shell.

- **Permissions:** exactly those of the SSH user, nothing more. Unlike the read-only `fileView` above, browsing is not limited to the home or project folder and secrets are not hidden: it is the person's own account, like `sftp` on a laptop. Downloading a file that looks like a key, credential or `.env` asks first, because the phone's 下载 folder can be read by other apps.
- **No path interpretation:** every path is one SFTP request argument, never a shell string. JSch expands `*` and `?` and removes backslashes in most of its calls (ls, stat, lstat, get, put, rm, rmdir, rename, hardlink, chmod), so the app escapes exactly those characters there (mkdir and realpath take the bytes as given). A file named `a*b?` is that file; a pattern can never match, delete or overwrite other files (checked against OpenSSH in the instrumented test). Names typed on the phone are one path component (no `/`, `.`, `..`, control characters, ≤ 255 bytes); names of picked phone files are cleaned like attachments (separators become `_`, bidi/format/control characters dropped) but may start with a dot.
- **No silent overwrite:** an upload goes to a hidden temporary file (`.herdr-pocket-<random>.part`) in the target folder, its size is checked against the bytes read on the phone, and only then it is moved into place. A taken name asks 替换 / 保留两个 / 跳过 first; native code checks again at the move: "new" and 保留两个 use OpenSSH's `hardlink@openssh.com` (fails atomically when the name exists; without it, a check followed by a plain rename, a small race), 替换 only replaces a regular file (never a folder or link), keeps its permission bits and uses `posix-rename@openssh.com` (atomic; without it the old file is removed first). Renaming never lands on an existing name. The temporary file is removed on any failure or cancel, from a fresh channel.
- **Deleting:** a file or a link (the link itself, never its target) after a confirmation; a folder only when empty. A folder with things in it needs its name typed; the tree is then walked first without following links, refused before anything is deleted when it holds more than 10 000 items, and removed deepest first. The first failure stops and says how many were already deleted. `/` and the home folder are never deleted.
- **Downloads** are written into a MediaStore Downloads row (`Download/Herdr Pocket`, Android 10+) that stays pending (invisible as a finished file) until every byte arrived, or into a document the person created with 另存为 (Storage Access Framework). The byte count must equal the size the computer reported; on a mismatch, a cancel or any error the row or document is deleted, so no partial file is left behind. Free space is checked first; files over 200 MB ask before starting. 打开 / 分享 hand only that document's URI to other apps, with a one-time read grant; the page never supplies a URI.
- **Uploads** read picked documents through the system picker (no storage permission). Read access is held (persistable grant) only until the upload ends, then released.
- **Transfers** run in the app process, two at a time, so they continue while the page changes; the page only polls counters (names, sizes, states). If Android ends the app, a transfer stops: a pending download row is never finalized (Android deletes it), and an interrupted upload may leave its hidden `.part` file on the computer. File contents are never logged, cached or shown in the WebView; the 文件 sort and hidden-file choices are kept per computer in the encrypted local cache.

## Local cache on the phone

To show something immediately on launch, the app caches the last session list, the first page of the history catalog and the most recent part (up to 80 messages) of chats the user opened. Cache entries live in the app's no-backup files directory, one subdirectory per saved device, with hashed file names, encrypted with AES-GCM under a separate Android Keystore key (`pocket.cache.v1`). Entries are capped at 1.5 MB each and 32 MB in total, evicting least recently used entries first. Deleting a device deletes its cache; Settings can clear the whole cache. A decryption failure (key removed, file damaged) discards the entry. Demo mode never writes the cache.

Cached content is display only: while SSH is still connecting the cached chat is read-only and no input can be sent; send targets always come from a fresh read after the connection is up. Native cache calls are scoped to the connected device or a device saved in the encrypted vault.

## History and bundled UI

History access is limited to JSONL files within the SSH user's `~/.codex/sessions` and `~/.claude/projects`. (The one exception, a file opened on explicit request in the read-only viewer, is described under "Viewing project files" below.) Remote requests use catalog-issued SHA-256 record IDs, not filesystem paths. Symlinks escaping the roots are rejected. To tell which conversation a live Codex pane is showing, the bridge also reads thread names from `~/.codex/session_index.jsonl` and the file names (thread IDs) in `~/.codex/thread-writer-locks/`; it never opens the lock files or any Codex auth/config file. The account endpoint returns only SSH username and hostname; no provider authentication/config files are read.

Adapters exclude system/developer messages, private reasoning and internal guardian records. Commands/results are historical evidence, never executable UI. Text uses DOM text nodes, not HTML interpolation. Transcript sources are private third-party formats and remain version-sensitive.

Update checks: besides the user's own SSH host, the app's only network traffic is the update check against `api.github.com/repos/HFO4AR/herdr-pocket/releases` (on launch at most every 12 hours, can be turned off in 设置, no device or account data sent) and, when the user taps update, the APK download from that repository's releases. A download is handed to the Android installer only if its SHA-256 matches the release's published digest, its package name is ours, its version code is newer and it is signed by the same certificate as the installed app; the system installer still asks the user to confirm. These requests run natively, never from the WebView.

The Android WebView only runs UI assets packaged in the APK, with network loads, external navigation, file/content access and frames blocked. CSP disables external scripts/resources. Native RPC results are JSON values, never concatenated HTML. UI tests contain fake devices only. Encrypted data is excluded from Android backup; losing the Keystore key means saved credentials need to be entered again.


The SSH terminal opens a PTY only on explicit user action. It supports arbitrary shell input as a user terminal, including destructive commands; commands are never synthesized or automatically replayed. Output uses a bounded in-memory ring. xterm.js and its styles are bundled offline, with OSC 52 clipboard access suppressed. Closing the independent shell may terminate programs in it; returning to the list does not close it. Herdr pane input targets are revalidated and require durable UUID receipts.

## Live tmux attach (实时)

- 实时 opens a **real tmux client**, only for a plain pane the person taps or chooses in the header. It is a PTY running the installed bridge with `--tmux-attach <pane id> <identity> [--read-only]`; before `exec` the bridge re-lists exactly that pane on its live tmux server and requires the same identity (server pid, pane id, pane pid). A stale or mismatched pane prints `没连上：…` and starts no client. Only that SSH user's own servers are reachable, as for every tmux operation.
- 实时 · 只读 uses `tmux attach -r`: tmux discards input from a read-only client, and the page refuses to write to it as well. A read-write client is a real tmux client like `tmux attach` on a laptop: keys typed on the phone go straight to the session, are **not** receipt-backed mutations, and are not buffered, retried or replayed; `^B` is tmux's own prefix. It shows the session's current window, which is not always the tapped pane (the app says so). Leaving the screen, or losing the SSH connection, detaches the client only; the session and the programs in it keep running. Nothing is killed or reconfigured automatically from this view.
- Terminal keys from the key bar and a hardware keyboard are mapped to xterm bytes on the phone, or to Herdr/tmux key names by the bridge (see PROTOCOL.md). A combination with no key code is refused with `没发出去：…`; it is never approximated by another key.

The connection password dialog can now persist the supplied password after successful authentication. Failed authentication does not overwrite the saved secret. Passwords remain absent from device list responses and UI output.


For explicitly authorized ch-cli remote history access, the bridge reuses transport metadata from the live SSH attach process, with `BatchMode=yes`, strict host-key checking and forwarding disabled. It never copies or reads private-key contents, provider auth/config files, or process environment. Remote history roots remain the corresponding SSH user's `~/.codex/sessions` and `~/.claude/projects`. To find the live conversation the remote side reads only ch's non-secret tmux locator fields (`socket`, `session`, `pane`, `pid`, `start`) from the route's `session.sqlite`, lists that tmux session's panes, and reads `/proc` argv and FD link names of the native agent process; it never reads process environment, the ch bridge token or task file contents. Automatic resolution parses only the matched transcript, and the candidate list parses only the Claude project directory belonging to that route workspace. One more file may be read there: the ch transfer copy (`~/.local/share/ch/transfers/<uuid>/<session uuid>.jsonl`, a real, non-symlinked, regular file of that user, plus its own `subagents/`) that the pane's native Claude process names in its own argv (`--resume <path>`); record IDs for it are opaque SHA-256 digests like the others and its path is not sent back. The route used for history may also come from the argv of ch's local relay while it reconnects; prompts, keys and files still require the live SSH attach. The bridge keeps remembered history links (record metadata only, no conversation content) in `~/.local/state/herdr-pocket/links-v1.json` (0600, written atomically under a lock); the `link` operation writes only that file, after re-listing the chosen record on the computer that holds the pane's history. The adapter does not persist any remote cache of history data.

To keep remote reads fast (a fresh SSH login over a slow link takes seconds), two things are reused:

- **One SSH connection per route, owned by the bridge.** Reads multiplex over a control socket in `~/.herdr-pocket/ssh/cm-%C` on the computer running the bridge (folder 0700, owned by the user, not a symlink; otherwise the read connects without reuse). The route's own `-S`/control path and the user's ssh config control path are never used; the connection keeps `BatchMode=yes`, strict host-key checking and forwarding disabled, closes itself after 5 idle minutes, and is torn down after a timeout. If ssh itself fails on the shared connection, the read (never a write) is retried once over a fresh unshared connection. File copies to the other computer do not use the shared connection.
- **A content-addressed copy of the read adapter on the other computer.** The only remote command is a fixed loader that receives the adapter's SHA-256 as its argument and the request on stdin. It runs `~/.herdr-pocket/bridge/<sha256>.py` only if that file is a regular, non-symlinked file owned by the SSH user, not group/world-writable, and its bytes hash to exactly that SHA-256; otherwise it reports the copy missing and the bridge ships the adapter on stdin (verified against the same hash before it runs) and the adapter stores itself there atomically (folders 0700, file 0600). Only files named `<64 hex>.py` in that folder are pruned, keeping the newest three versions. The adapter is the public bridge source; it contains no credentials or request data.

Account display remains the primary SSH connection's username/hostname.

Remote record identifiers are bound to a rediscovered live route; the app cannot supply an arbitrary SSH destination or filesystem path. A unique dedicated ch-cli route workspace can identify its one native conversation. Generic cwd matches and ambiguous routes provide explicit read-only choices. Selecting history does not resume a provider session or send input. Temporary SSH/read failures remain visible and do not authorize mutation replay.

## Viewing project files (read-only, 0.6)

Besides history, the bridge can read one **project file** for display. This is opt-in per tap: a path in a message opens a sheet, and only tapping 「查看文件内容」 there sends a `fileView` request for that one file. Nothing is read ahead of time, in the background or for previews, the content is not written to the phone's cache, and the operation never writes, executes or lists anything. Searching inside a conversation runs on the phone over messages already loaded; it reads no files.

The `fileView` operation enforces, on the computer that has the file:

- **Where:** the path (absolute, `~/…`, or relative to the conversation's working directory) is resolved with `realpath`, so every symlink is followed, and the result must lie inside the SSH user's home folder or the conversation's project folder (the `cwd` recorded in the transcript the app has open, looked up by its record ID; a working directory sent by the app is only a base for relative paths, never an allowed root). `/` is never a root. A link that leads out of these folders is refused ("链接指向项目和主目录之外").
- **Never secrets:** refused by the requested path and again by the resolved path: anything under `.ssh`, `.gnupg`, `.aws`, `.password-store`, `.kube`, `.docker`, `~/.config/gh`, `~/.local/share/keyrings`; provider sign-in/config files (`~/.codex/auth*`, `~/.codex/config*`, `~/.claude/.credentials*`, `~/.claude/settings*`, `~/.claude.json`); and files named `.env*`, `*id_rsa*` / `*id_ed25519*` / `*id_ecdsa*` / `*id_dsa*`, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `*.jks`, `*.keystore`, `*keystore*`, `*.kdbx`, `*.ppk`, `.netrc`, `.pgpass`, `.git-credentials`, `.npmrc`, `.pypirc`, `credentials*`. The app shows "这是密钥、凭据或 .env 一类的敏感文件，不在手机上显示". This list cannot recognise every secret: a token pasted into an ordinary source file is shown like the rest of that file.
- **Only regular files:** directories, devices, pipes and sockets are refused before opening; the file is opened with `O_NOFOLLOW | O_NONBLOCK` and must still be the same regular file.
- **Bounded:** at most the first 512 KB are read and sent (the app says the file was cut and how big it is). Files with NUL bytes or mostly undecodable/control bytes are reported as binary and their content is not sent.

For a pane on another computer (ch-cli route), the same request goes through the remote read path described above (the stored, hash-checked adapter over the bridge's own SSH connection, request on stdin), and the same checks run on that computer against that SSH user's home folder, the route's workspace folder and the transcript's working directory there.

## Background tasks: status and output (read-only, 0.6)

The app shows which background shells, monitors and terminals an agent started (「后台任务」) and whether they still run. The **status** comes from the agent's own transcript, read incrementally like sub-agents (the `glance` and `history` operations; a small bounded state file in `~/.local/state/herdr-pocket/kids-v1.json` remembers the read offset, at most 80 tasks per conversation and 64 conversations). To tell a Claude shell that was stopped from Claude's UI (which writes no record) from one that still runs, the bridge lists which `*.output` files the SSH user's own processes hold open (`/proc/<pid>/fd` link targets of processes with the same uid; nothing else about those processes is read or kept).

The **output** of one task is read only when the person taps it (and while that viewer stays open on a running task, again every 5 s, or on 「刷新」), with the `bgOutput` operation. It never writes, stops, signals or lists anything, and the text is not written to the phone's cache. It enforces, on the computer that has the transcript:

- **Only this task's own file:** the request names a conversation record (provider, thread, record ID, as for `history`) and a task id. The bridge reads the output path that this transcript itself recorded for that task id (Claude's "Output is being written to: …" or the task notification's `<output-file>`); a path sent by the app is never used. That path must be exactly `<tmp>/claude-<the SSH user's uid>/<project>/<this conversation's session id>/tasks/<this task id>.output`, the `claude-<uid>` folder must be a real folder (not a symlink) owned by that user, and the `realpath` of the file must equal that same path below it, so no symlink anywhere from `claude-<uid>` down (a link to another file, or a linked `tasks` folder, is refused). A task id from another conversation is "这段对话里没有这个后台任务".
- **Only a regular file of that user:** opened with `O_NOFOLLOW | O_NONBLOCK`; it must be a regular file owned by the SSH user.
- **Bounded and plain:** only the last 64 KB are read and sent (from a line start); colour/cursor escape sequences and control characters are removed and the text is shown as text.
- A running Claude monitor has no recorded output file yet: its viewer shows the newest event text from the transcript (kept, at most 1.5 KB, in the state file). Codex writes no output files: its viewer shows the newest output Codex itself received for that terminal, re-read from the one rollout line whose byte offset the scan recorded (at most 64 KB sent).

For a pane on another computer (ch-cli route), `bgOutput` goes through the same remote read path as history (stored, hash-checked adapter, request on stdin) and the same checks run there with that SSH user's uid and transcripts. The background watcher only asks for counts (`bg.hold`), never output.

## Permissions and pane input (0.6)

- Photos: pictures come from the system photo picker, which grants access to what was picked; no storage permission is used. Some galleries (seen on MIUI) return a storage path or a provider that checks the photos permission instead. Only when reading such a picked picture is refused does the app ask for the standard photos permission (`READ_MEDIA_IMAGES`, or `READ_EXTERNAL_STORAGE` up to Android 12) and retry just those pictures. "All files access" is never requested.
- ch panes: the agent runs on another computer behind ch's local relay, so Herdr lists it but refuses its agent commands (`agent_not_ready`: not the pane foreground process). Only after that refusal (nothing was written) and only when the pane's process tree shows a ch route and no local agent process, the same input goes to the pane instead: `pane run` for one line, a single bracketed paste plus Enter for several lines, `pane send-keys` for keys. It is the one write for that request id; an unknown outcome is still never retried. A prompt to a Claude / Codex whose input box is readable on screen uses pane-level input from the start (local or relay alike, see below).
- 立即发送 sends Esc to a busy agent (Esc stops a turn in Claude Code and Codex and never quits them), waits until Herdr reports the same agent stopped, then sends the message through the normal checked path. If the agent does not stop within 20 s, nothing is sent.

- /status and /usage on Claude: Claude Code shows these as a tabbed panel. Only as a direct consequence of the person sending `/status` or `/usage` from the phone, once, the bridge `panelTour` walks that panel so the card can show every tab: → between tabs, ↓ / ↑ to scroll the plain-text Status / Usage tabs, Esc to close. Nothing else is pressed (never Enter, Space, letters or Tab, never anything on Config's search box or settings list, and Config is never scrolled), each key waits for a re-read that shows the panel with its focus on the tab row, a receipt is written first and an unknown outcome is not replayed. It is refused, with no key sent, when the agent is not idle, another dialog is up, the focus is elsewhere or the panel is not on screen; a screen that no longer shows the panel gets no Esc. No other command or screen is automated this way.

## tmux sessions (0.6)

- The 会话 list also shows the SSH user's own tmux panes, from every tmux server that user runs: the **default** server (no `-L`/`-S`; `$TMUX` is dropped so a bridge started inside tmux does not pick another server; `TMUX_TMPDIR` is honored like tmux does) and **named** servers (`tmux -L name`), found as sockets in the user's tmux socket directories only: `$TMUX_TMPDIR/tmux-UID`, `/tmp/tmux-UID`, `/private/tmp/tmux-UID` (macOS), `$XDG_RUNTIME_DIR/tmux-UID` and `/run/user/UID/tmux-UID`.
- Socket checks, with `lstat` only (no symlink is ever followed): the directory must be a real directory owned by the SSH user and not group/world-writable; a socket must be a real unix socket owned by that user. Anything else is skipped and reported by path and reason (`skipped`), never used. At most 16 named servers are read, in parallel, each with a 3 s limit; a dead socket answers "no server" at once and is left out. A named server is addressed with `-S <socket path>` as one argv item. Other tmux sockets of the user (for example ch's own `/tmp/ch-native-UID-*/tmux.sock`, which holds ch's route sessions behind the Herdr pane that attaches to them) are not in these directories and are never read. tmux on another computer is not listed: add that computer as a device.
- Panes running the Herdr client are left out. Nothing starts a tmux server except 「新建 tmux 会话」 (default server only): only `list-panes`, `capture-pane`, `send-keys`, `load-buffer`/`paste-buffer`/`delete-buffer`, `kill-pane`/`kill-session` are run, as argv lists, never through a shell. The list reports the directories it read (`looked`) so an empty list can say where it looked; these are paths of the SSH user's own tmux directories.
- A pane is addressed by tmux's id (`%N`; on a named server `%N@<12 hex>`, the first 12 hex digits of a hash of its socket path, since every server numbers panes from `%0`; checked strictly) plus an identity hash of the server pid, pane id and pane pid, plus the socket path for a named server. The bridge re-lists that one server before every read or write, so a closed pane whose id comes back, or the same `%N` on another server, is never written to.
- The screen is `capture-pane -p -e -J` with up to 200 lines of scrollback, reduced to SGR colors like agent screens (no OSC, cursor moves or other escapes reach the UI).
- Input is a real keypress in that pane, like typing on the computer: text is sent literally (`send-keys -l --`), several lines as one paste (a temporary named buffer, deleted after pasting), keys from a fixed list (arrows, Enter, Esc, Tab, Backspace, Ctrl+C, Ctrl+D). Each send needs a UUID with a receipt committed first; a failure after the first write is reported as unknown and never retried.
- **Agent input box (Herdr and tmux)**: the phone's message replaces text in a Claude / Codex input box instead of being refused (the person asked for that), but never by guessing: only the editing keys `ctrl+e ctrl+u ctrl+k backspace` are pressed (never Esc, Ctrl+C, Ctrl+D or arrows), and only once the receipt is written; the box must then read empty on the coloured screen, else nothing is pasted (`没发出去`). The person's own draft on the computer is lost that way — a deliberate trade, stated in the app's note 「覆盖了它输入框里原来的字」. Enter is pressed only when the screen shows the box holding exactly this message; a second Enter only when the box still shows the same text unchanged (it was not taken); the message is never pasted twice, and an unconfirmed outcome is reported, never replayed. A question or approval dialog on screen still refuses before anything is typed.

## Starting Herdr and the Herdr guard (启动 Herdr / Herdr 守护)

The Herdr server of the default session can be killed under the person (the kernel OOM killer, systemd-oomd, a crash), and with it every pane and agent. The person asked for a way back from the phone and for an opt-in guard.

- **Reading the state** (`herdrHealth`, read-only): `herdr status --json`, the end of Herdr's own log next to its socket (`herdr-server.log`: the `app.startup` / `app.shutdown` lines and their pids, read backwards, at most 16 MB), `/proc/stat` (boot time), `/proc/net/unix` (whether something still holds the server socket open), and, only to explain a run of the last 7 days that ended, `journalctl --since <its start> -g …` for that pid: the kernel's "Killed process <pid> (herdr)", an earlyoom line naming the pid, or a systemd-oomd kill of the cgroup the server was last seen in. Lines are matched in the bridge and only the matching line (≤ 300 characters) is returned. Without permission to read the system journal the cause stays "unknown"; nothing is escalated. `systemctl --user is-system-running / is-active / is-enabled / show`, `systemctl show user@<uid>.service -p OOMScoreAdjust`, `loginctl show-user <user> -p Linger`, `busctl get-property … KillUserProcesses` and `crontab -l` (to find our own marked lines) are read the same way. No server socket path, process environment or pane content is sent to the phone.
- **启动 Herdr** (`herdrStart`, a UUID receipt like every mutation): refused unless `herdr status` says the default server is not running and no process holds its socket (a server that is starting or hung is never doubled); one start at a time through a lock shared with the guard (`~/.local/state/herdr-pocket/herdr-start.lock`). It runs exactly `herdr server` (Herdr's own headless server; a second one refuses by itself), with `HERDR_*` and `SSH_*` variables removed from its environment, in the home folder, stdio on `/dev/null`: as a transient systemd user service `herdr-pocket-server` (`systemd-run --user --collect`, own cgroup, `OOMScoreAdjust=` the lowest value the system lets user units ask for) when the user lingers, otherwise in a new session (`setsid`) so it outlives the SSH request (unless logind's `KillUserProcesses=yes` ends a logged-out user's processes, which the sheet says). The phone never starts it on its own and never retries.
- **Herdr 守护** is installed only by 「开启守护」 after a sheet that shows every file path and its full content, the crontab lines and the commands that will run; `guardSet` carries the digest of that plan and is refused (nothing written) if what would be installed differs. It writes:
  - `~/.herdr-pocket/guard/herdr-guard.py` (0600; the public source embedded in the bridge, standard library only), and
  - with a systemd user instance: `~/.config/systemd/user/herdr-pocket-guard.service` (or under `$XDG_CONFIG_HOME`), marked as ours, `ExecStart=<python3> -I <script> --watch --herdr <herdr path> [--boot] [--always]`, `Restart=on-failure`, `KillMode=process`, `WantedBy=default.target`; then `systemctl --user daemon-reload`, `enable` and `restart` of that one unit. A unit file at that path that we did not write is never overwritten or removed; a failed step removes what was written.
  - without systemd: two lines in the user's crontab, each ending in `# herdr-pocket-guard` (`@reboot … --once --boot` and `* * * * * … --once`, output to `/dev/null`); other lines are kept as they are and read back.
- **What the guard does**: every 10 s (cron: every minute) `herdr status server --json`. While Herdr runs it does nothing but note which run is up (pid, start time, cgroup) in `~/.local/state/herdr-pocket/guard-v1.json` (0600; times, pids, reasons, the last 30 events, no content). When the server is gone it reads Herdr's log: a run without a logged clean shutdown (killed, crashed, out of memory) or a memory kill found in the journal is started again with the same start routine as 启动 Herdr (systemd: its own `herdr-pocket-server` unit; cron: `setsid`); a clean shutdown while the guard watched (`herdr server stop`, SIGTERM) is left alone unless 「正常关掉的也拉起」 (`--always`) was chosen; a run that ended before the guard started (reboot, new login) is started only with 「登录或开机后也启动 Herdr」 (`--boot`). Starts back off (10 s, 30 s, 1 min, 2 min, then every 5 min while it keeps dying). It never stops, restarts or signals a Herdr process, never starts a second server, never touches panes or agents, and only guards the default session.
- **OOM protection**: a user unit can lower `oom_score_adj` only down to what root gave the user's systemd instance (`user@<uid>.service` `OOMScoreAdjust`, 100 on Fedora; user units default to 200), checked by reading both values; lowering further (e.g. -500) needs root and is not attempted. The guard asks for that floor only when it is below the default, the sheet says so, and the processes in Herdr's panes inherit it. No `MemoryMax`/`MemoryHigh` is set: a limit on Herdr's unit would hit the agents and builds in its panes, causing the kills it is meant to prevent.
- **Linger**: without `loginctl enable-linger` the user's systemd instance (and so the guard and a server it started) only runs while the user is logged in somewhere; the sheet says so and shows the command. The app never runs it or anything with sudo.
- **关闭守护** (`guardSet` with `enable: false`, its own receipt): `systemctl --user disable --now herdr-pocket-guard.service` (with `KillMode=process` this stops only the watcher), deletes our unit file, `daemon-reload`, removes our crontab lines, the script and `guard-v1.json`. A Herdr server the guard or 启动 Herdr started keeps running (`herdr-pocket-server` is a separate transient unit that goes away when Herdr exits).
- **What comes back**: a started Herdr restores its saved workspaces and tabs from its own `session.json`, and Herdr itself may reopen agent panes in their previous conversations (its `[session] resume_agents_on_restore`, on by default in 0.8.2, for agents with an installed Herdr integration). That is Herdr's behaviour; Herdr Pocket sends nothing to any pane, and the phone only compares the agents listed before and after (agent session ids) to say which came back.
- macOS and other systems: the guard reports unsupported; 启动 Herdr still works (setsid).

## Resuming a conversation (继续这个对话)

- **The phone names a conversation, never a command.** `create` / `tmuxNew` take `resume: {id}` (Claude / Codex) or `{id, host}` (ch). The id must be a lowercase UUID; a ch host must match `[A-Za-z0-9][A-Za-z0-9_.-]{0,62}` and be a `[hosts.<name>]` table of the SSH user's `~/.config/ch/config.toml` (only the table names are read, never targets or key paths). Anything else, extra keys or another agent kind are refused before any receipt (`没继续：…`).
- **Only conversations of this account.** A Claude / Codex id must be a root conversation in the approved transcript roots (sub-agent records cannot be resumed). The start directory is checked like `create`'s (existing, enterable, real path).
- **No shell interpolation.** Herdr gets the agent arguments as separate argv items after `--` (`claude --resume <id>`, `codex resume <id>`); the ch line typed with `pane run` and the line typed into a new tmux session (`send-keys -l` then `Enter`) are fixed words plus the two checked tokens, each passed through `shlex.quote`. The phone never supplies flags (no `--dangerously-skip-permissions` or similar can get in).
- **No double start, no replay.** Before the receipt the bridge looks at the SSH user's own processes (`/proc/<pid>/cmdline`, and for Claude only the FD link names of its runtime task folder): a Claude or Codex TUI already holding that conversation, or an SSH attach to that ch session, refuses with `没继续：这段对话已经在运行了…`; the Codex app-server is ignored since it keeps rollouts open. A request id answers from its receipt before these checks, so a retry reports the pane it made instead of starting another; an unknown outcome is never retried by the app. Bulk 全部继续 sends one request at a time after a confirmation listing every conversation.
- **What the phone keeps:** the list of conversations seen running per computer (kind, id, ch host, directory, title, pane id / terminal id, times) lives in the encrypted local cache (LocalCache), at most 40 entries for 7 days; 设置 → 清除缓存 removes it. It is only used to offer 「最近断开的」; nothing is resumed without a tap.

## Feedback diagnostics

设置 → 帮助与反馈 → 反馈问题 builds a plain-text summary only when tapped, shows it in full, and copies it or opens `github.com/HFO4AR/herdr-pocket/issues/new` only on a further tap (nothing is attached to the URL). It holds the app, Android and WebView versions, the bridge's own version/protocol/Python version (read-only `hello`), whether Herdr is installed and how many sessions run (read-only `doctor`), fixed state words, counts, settings and up to eight recent native error **codes** with the operation name. Error messages are never kept, because they can name hosts, users or paths; codes and operation names must match strict patterns before they are stored, in memory only. Device names, host names, user names, paths, titles, message text, keys and fingerprints are never included.
